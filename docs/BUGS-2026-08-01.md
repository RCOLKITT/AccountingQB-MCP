# AccountingQB — Bug Report, 2026-08-01

Found during a live end-to-end session: Stripe revenue sync + credit card reconciliation
against NutriFitAI LLC (realm `9341453706844727`, ~230 card transactions YTD).

All line numbers refer to `mcpb/src/accountingqb/server.py`.

**Headline:** three of these bugs each independently produced a *confidently wrong answer*
rather than an error. Together they caused a four-turn misdiagnosis in which the assistant
told the user their bank feed had died, that they were missing $4,500 of payments and
~$7,500 of deductions, and sent them to audit their For Review queue. None of it was true.
All of the data was in QuickBooks the whole time.

The unifying theme: **this server fails silently and reports partial or wrong results with
full confidence.** For an accounting tool that is the worst possible failure mode. A tool
that errors is recoverable; a tool that lies is not.

---

## P0 — Silent truncation in `qb_account_transactions`

**Location:** line 5897, query construction at 5929-5936

```python
"Purchase": f"SELECT * FROM Purchase WHERE TxnDate >= '{start_date}' AND TxnDate <= '{end_date}' MAXRESULTS {max_results}",
```

`MAXRESULTS` with **no `STARTPOSITION` pagination and no `ORDER BY`**. QuickBooks returns
the first N records for the range; the function then filters those N to the requested
account *in Python* and reports the survivors as a definitive count.

### Repro

```
qb_account_transactions("Delta Platinum Business Card", "2026-03-05", "2026-08-01")
  → "Transactions Found: 17"          # WRONG

qb_account_transactions("Delta Platinum Business Card", "2026-03-05", "2026-08-01",
                        max_results=1000)
  → "Transactions Found: 230"         # correct
```

The 17 were the account-matching subset of the oldest 100 Purchases in the range. Every
July transaction (IDs 2202-2249) was outside the fetched page and simply did not exist as
far as the caller was concerned.

### Why this is P0

This is the primary reconciliation tool. It is what a bookkeeper uses to answer "does this
account tie?" It returned a plausible-looking register, with a header stating a specific
count, that was missing 93% of the data. There was no warning, no ellipsis, no indication
of truncation.

### Fix

1. Loop `STARTPOSITION` in pages of 1000 until a page returns fewer rows than requested.
   Do this for **all six** entity types in the `txn_types` dict, not just `Purchase`.
2. Filter to the account inside the loop so memory stays bounded.
3. Until pagination lands, if any entity query returns exactly `max_results` rows, refuse
   to print a total and return an explicit truncation warning instead.

### Audit the same pattern elsewhere

`MAXRESULTS` without pagination appears in at least:

| Function | Line | Default | Risk |
|---|---|---|---|
| `qb_account_transactions` | 5897 | 100 | **confirmed broken** |
| `qb_list_accounts` | 2829 | 100 | CoA here is ~110 accounts — **likely already truncating** |
| `qb_search_transactions` | 1949 | 50 | very low default |
| `qb_uncategorized_transactions` | 3585 | 100 | |
| `qb_find_duplicates` | 3638 | 200 | duplicate detection across a truncated set is meaningless |

`qb_list_accounts` truncating is its own hazard: a duplicate-account check was run during
this session and came back clean. With ~110 accounts against a 100 cap, that result cannot
be trusted.

## P0 — `_resolve_account` silently returns the wrong account

**Location:** lines 1061-1078

```python
result = await qb_query(
    f"SELECT * FROM Account WHERE Name LIKE '%{safe}%' MAXRESULTS 1")
```

For an unqualified name there is no exact-match attempt and no ambiguity check — just a
substring LIKE, capped at one row.

### Repro

```
qb_create_journal_entry(..., lines_json='[{"account_name": "Services", ...}]')
  → posts to "Legal & accounting services"     # an EXPENSE account
```

$195.00 of revenue was posted into an expense account. The entry balanced, so nothing
downstream flagged it. It was caught only because the P&L income section looked wrong on
manual inspection.

### The same input is handled correctly elsewhere

`qb_account_transactions` (line 5912):

```python
if len(accounts) > 1:
    return f"Multiple accounts match: {names}. Please be more specific."
```

Two resolution paths exist and only one is safe. The safe one is not the one used by the
write tools.

### Fix

1. Exact `Name` match → exact `FullyQualifiedName` match → `LIKE` only as last resort.
2. Drop `MAXRESULTS 1` on the LIKE branch. If it returns >1, return the ambiguity error.
3. Consolidate both paths onto a single resolver.

**Blast radius:** every write tool taking an account name — journal entries, expenses,
bills, deposits, transfers, reclassifications.

## P1 — Unknown parameters silently discarded (systemic)

Three separate instances of the same root cause. Callers get no signal that an argument
was ignored.

### `qb_create_journal_entry` line keys

**Location:** lines 3129-3131

```python
acct_name = entry.get("account_name", "")
amount    = float(entry.get("amount", 0))
posting_type = entry.get("type", "Debit")
```

Passing `posting_type` instead of `type` silently defaulted **every line to Debit**. The
balance check caught it by luck. A symmetric mistake would post cleanly and wrong.
Passing `account_id` instead of `account_name` was likewise ignored.

### `qb_list_accounts` has no `account_type` parameter

**Location:** line 2829 — signature is `(max_results: int = 100)`.

An `account_type="Bank"` argument was accepted and dropped; the call returned the entire
chart of accounts. Calling it twice with `"Bank"` and `"Credit Card"` produced byte-identical
output, which is how the discrepancy surfaced.

### Fix

1. Validate line-item dicts against a schema; reject unknown keys with a message naming
   the valid ones.
2. Accept `account_id` as an explicit, unambiguous alternative to `account_name` —
   this alone would have prevented the P0 above.
3. Add a real `account_type` filter to `qb_list_accounts` (and `active_only` while there).
4. Audit every tool for kwargs accepted but unused.

## P1 — `qb_search_transactions` misses bank-feed memos

**Location:** lines 1949-1961

```python
"memo": p.get("PrivateNote", ""),
```

Bank-feed descriptors live on the **line Description**, not `PrivateNote`. So the text that
`qb_account_transactions` and `qb_transaction_detail` both display as "Memo" is not what
search actually searches.

### Repro

```
qb_search_transactions("2026-01-01", "2026-12-31", "MOBILE PAYMENT")
  → "No transactions found"
```

There are **14** matching transactions totalling **$8,500**.

### Fix

Search line-level `Description` in addition to `PrivateNote`, and concatenate both into the
searchable blob. Note the 50-row default cap compounds this (see P0).

## P2 — `qb_books_health_audit` scores 100/100 on materially broken books

The audit returned a perfect score while all of the following were true:

- $1,500 of transactions categorized to a **deleted account**
  (`Delta SkyMiles® Reserve Card (1008)`, via Purchases 2037 and 2021)
- 14 credit card payments recorded as **Purchases**, inflating the liability rather than
  reducing it — a ~$17,000 swing
- A bank account carrying **−$36,123** whose only activity all year is seven $0.11 interest
  deposits, i.e. an opening-balance error
- Two bank accounts and one credit card with negative balances in the wrong direction
- Duplicate accounts, misclassified account types, inverted equity signs (from an earlier
  hygiene review)

### Proposed "Books Hygiene" tier

Checks that would each have caught something real here:

1. **Dangling references** — any transaction categorized to an inactive/deleted account.
2. **Sign sanity** — asset accounts with credit balances, liabilities with debit balances,
   contra-equity pointing the wrong way.
3. **Payment direction heuristic** — a Purchase on a credit card whose category is an
   equity or bank account is almost always a misfiled payment. Flag it.
4. **Feed-velocity drop** — alert when an account's monthly transaction count falls off a
   cliff versus its trailing average. (Would have been a false positive here, but it is
   the correct check for the real version of this failure.)
5. **Dormant account with large balance** — nonzero balance plus near-zero activity is an
   opening-balance error, not a real position.
6. **Balance attestation** — prompt for the institution's actual statement balance and diff
   it against QuickBooks. This is the only check that catches everything above at once and
   it is the single highest-value item on this list.

## Feature: `qb_stripe_reconcile`

The Stripe→QuickBooks sync done manually this session is entirely mechanical and is the
single most common bookkeeping task for any SaaS or e-commerce client.

**What it should do:** pull charges, refunds, payouts **and all balance-transaction types**;
create/reuse a processor clearing account; post monthly journal entries; then assert that
the clearing balance equals the live processor balance.

**Where the differentiation is — platform fees.** Most implementations net revenue against
processing fees and stop. They miss Sigma, Billing, Radar, Connect, Tax and Terminal fees,
which is why their clearing account never ties. On this account those fees were **$33.86
against $10.10 of processing fees — more than 3× larger** than the fees everyone actually
books. The reconciliation only closed because they were included.

Generalize to a processor-clearing concept covering Stripe, PayPal, Square, Shopify Payments.

## Suggested order

1. `qb_account_transactions` pagination — plus the audit of every other `MAXRESULTS` call site
2. `_resolve_account` exact-match + ambiguity error
3. Unknown-parameter rejection across all tools; add `account_id` to JE lines
4. `qb_search_transactions` line-Description coverage
5. Books Hygiene tier, starting with balance attestation and dangling references
6. `qb_stripe_reconcile`

Items 1-3 are correctness bugs in a product whose entire value proposition is that the
numbers are right. They should block the next release.
