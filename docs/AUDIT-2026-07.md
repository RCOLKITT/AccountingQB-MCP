# AccountingQB Product Audit — July 2026

Scope: (1) why users sign up but never get connected, (2) what it takes to support Canadian
bookkeepers, (3) how the latest MCP/AI ecosystem changes the best distribution and setup
architecture. Findings are based on the codebase, the live Supabase licensing database,
Vercel production logs, and current Intuit/Anthropic/MCP documentation.

---

## Executive summary

- **The funnel is losing ~75% of paying signups before first value.** Live data: 12 licenses
  issued since March, only 3 ever connected QuickBooks. Two of those 3 still canceled.
- **The single worst bug made successful connections look like failures**: the setup wizard's
  connection poll queried a database table that doesn't exist (`tokens` instead of
  `oauth_tokens`), so it always reported "not connected" — even after the user completed
  OAuth. Fixed in this branch.
- **The entire lifecycle email system has been dead since late April**: Clerk middleware
  blocked Vercel's cron requests with a 404, so welcome emails, day-3 check-ins, trial
  warnings, and payment-failure emails were scheduled but never sent (confirmed in Vercel
  logs: `/api/cron/process-emails` → 404 every 15 minutes). Fixed in this branch.
- **Canada is currently a hard no-go**, not a degraded experience: creating any invoice for a
  Canadian QuickBooks company fails with Intuit error 6000 ("Make sure all your transactions
  have a GST/HST rate"), and 7+ tax tools produce US-only (i.e., wrong) numbers. A concrete
  CA plan is below (~4–6 weeks to genuinely CA-ready; ~1 week to "works and doesn't lie").
- **Distribution should shift to a two-tier architecture**: a remote MCP connector (one-click
  OAuth, works in Cowork web/mobile, listable in Anthropic's Connectors Directory) as the
  growth funnel, plus the local `.mcpb` extension — ported off the fragile python/uv runtime —
  as the "your books never touch our servers" flagship tier.

## Part 1 — Why users sign up but don't connect

### Live funnel evidence (Supabase project `qb-mcp-licenses`, Vercel project `accounting-qb-mcp`)

| Stage | Count |
|---|---|
| Licenses issued (Mar 12 – Jun 9) | 12 |
| Ever connected QuickBooks (`oauth_tokens` / `qb_connected` milestone) | 3 (25%) |
| Currently active + connected | 1 |
| Canceled | 5 (incl. 2 of the 3 who *did* connect) |
| Lifecycle emails sent since Apr 27 | **0** (welcome 0/2, qb_connected 0/3, trial-4-day 0/3, day-3 0/2) |
| `invoice.payment_failed` Stripe events (through Jul 7) | 26 — dunning emails for these also never sent |
| Rows in `tool_usage` (ever) | 0 — usage tracking has never recorded a call |

### Root causes, ranked (✅ = fixed in this branch)

1. ✅ **Setup wizard could never detect a successful connection.**
   `web/src/app/api/oauth/status/route.ts:21` queried `.from("tokens")`; the real table is
   `oauth_tokens`. The query always errored → `{connected:false}` → the wizard polls this
   every 2s and, after 120s, tells the user the connection failed ("Taking longer than
   expected… check popup blocker") even when tokens were written successfully. Users who
   did everything right were told they hadn't.

2. ✅ **All lifecycle/onboarding email crons 404'd at the middleware.**
   `web/src/middleware.ts` didn't list `/api/cron(.*)` as public, so Clerk's `auth.protect()`
   rejected Vercel's cron invocations (they authenticate with `Authorization: Bearer
   CRON_SECRET`, not a Clerk session). Vercel logs show `/api/cron/process-emails` and
   `/api/cron/update-stats` returning 404 on schedule, all day, every day. Welcome emails
   (which contain the license key and setup link), day-3 nudges, trial warnings, and
   payment-failed emails silently queued forever.
   **Action required after deploy: confirm `CRON_SECRET` is set in Vercel env; then watch
   `email_schedules.sent_at` start populating. Decide whether to send or cancel the ~13
   backlogged emails (some trial warnings are now stale and would confuse recipients —
   recommend bulk-cancelling everything scheduled before today).**

3. ✅ **Every post-purchase CTA led to a Clerk sign-in wall.**
   Stripe checkout never creates a Clerk account, but `/dashboard` (the destination of the
   success page CTA, the license email CTA, and the setup pages) required Clerk auth. The
   dashboard's built-in signed-out "legacy license key" mode was unreachable dead code.
   `/dashboard(.*)` is now public; the page itself handles signed-out visitors.

4. ✅ **The advanced setup page told users to install a package that doesn't exist.**
   `/setup` instructed `uvx accountingqb-mcp` — that name is **not on PyPI** (the published
   package is `accountingqb`). Everyone who followed that page got "package not found."
   It also told self-hosters to register redirect URI `https://accountingqb.com/api/qb/callback`,
   a route that doesn't exist (real: `/api/oauth/callback`). Both fixed. Note the page still
   conflates hosted mode (license key) and self-hosted mode (own Intuit app) in one config —
   worth a redesign.

5. ✅ **License-key rotation was broken three ways** (`api/license/rotate/route.ts`):
   rejected all trial users (checked `status !== "trial"` but the DB value is `"trialing"`),
   wrote to columns that don't exist (`rotated_at`, `previous_key` → 500 for everyone), and
   generated keys in `XXXX-XXXX-XXXX-XXXX` format while issuance, docs, and the usage-tracking
   API all require `LK-<hex>`. All three fixed (old key remains auditable via `event_logs`).

### Remaining defects (not yet fixed — recommend next sprint)

6. **Clerk↔license linking only works by exact email match.** `user_profiles` has no
   `clerk_id` column, so the Clerk webhook's inserts/lookups fail silently
   (`api/clerk/webhook/route.ts`), and `api/user/licenses/route.ts` compares a UUID column
   to an email string. The only surviving path is an `ilike` on `licenses.email` — a user who
   signs up with a different email than checkout sees "No License Found." Fix the schema
   (add `clerk_id`), repair the webhook, and add a "claim license by key" flow for mismatches.
7. **Hosted users who haven't connected yet get the self-hosted error.** In
   `mcpb/src/accountingqb/server.py`, `_hosted_mode` is only true once ≥1 company exists, so
   a valid-license/no-connection user is told to "Set QB_CLIENT_ID, QB_CLIENT_SECRET…" —
   env vars they should never touch — instead of "connect at accountingqb.com or run
   qb_refresh_connection." Treat a present `QB_LICENSE_KEY` as hosted mode.
8. **Refresh-token rotation race.** `api/oauth/token/route.ts` refreshes all of a license's
   tokens in parallel and is called concurrently by server startup, per-tool calls, and the
   dashboard. Intuit rotates refresh tokens on every use; last-write-wins can orphan the
   live token and force intermittent re-auth ("it disconnected again"). Add single-flight
   locking (e.g., a `refresh_in_progress` row lock or advisory lock per license+realm).
9. **Webhook-only license issuance with no fallback.** License row + license email are both
   created inside `checkout.session.completed`. If the Stripe webhook is late or
   misconfigured, the success page gives up after 20s and the email never comes. Add a
   fallback: success page hits an endpoint that reconciles the Stripe session server-side.
10. **`NEXT_PUBLIC_BASE_URL` used in code but only `NEXT_PUBLIC_APP_URL` documented** in
    `.env.example`; OAuth redirects silently fall back to hardcoded `https://accountingqb.com`.
11. **Blocking 15s network call at MCP server import** (`_fetch_hosted_tokens()`); slow
    accountingqb.com = Claude Desktop may consider the server dead on launch. Lazy-load.
12. **`qb_switch_company` naive/aware datetime comparison** raises `TypeError` on first call
    after a switch (`mcpb/src/accountingqb/server.py:779` vs `:573`).
13. **Support-bot knowledge base is stale**: it walks users through manual
    `claude_desktop_config.json` editing with an "API key," contradicting the MCPB flow.
14. **`tool_usage` never receives rows** — verify the extension actually calls
    `/api/usage/track` (keys rotated to non-`LK-` formats were also rejected by it, see #5).

### Prerequisite friction (why even bug-free setup loses people)

- macOS/Linux path requires installing `uv` via a curl|sh command; Windows path requires
  installing Python via winget, then `pip install accountingqb`. For bookkeepers this is the
  single biggest non-bug drop-off, and the `.mcpb` itself assumes `uv` is already on PATH
  (`mcpb/manifest.json` `"command": "uv"`) — Claude Desktop bundles Node.js, **not** Python/uv.
  There is also a known Windows race bug with uv-based MCPB extensions. See Part 3: port the
  extension server to TypeScript, or fully bundle a venv per the MCPB spec.

## Part 2 — Supporting Canadian bookkeepers

### Why it's currently broken (both `server.py` and `mcpb/src/accountingqb/server.py`)

- **Hard blocker — sales transactions fail.** Canadian QBO uses the global tax model:
  every line needs `TaxCodeRef` and the transaction takes `GlobalTaxCalculation`
  (`TaxExcluded`/`TaxInclusive`/`NotApplicable`). None of `qb_create_invoice`,
  `qb_create_credit_memo`, `qb_create_estimate` set either → Intuit rejects with
  ValidationFault **code 6000**: "Make sure all your transactions have a GST/HST rate
  before you save."
- **No tax-code discovery.** There is no `qb_list_tax_codes`/`qb_list_tax_rates` tool, so
  even a knowledgeable user can't work around it through Claude. (CA companies come
  pre-seeded with codes per province: G, H, P, S, Q, E, Z, Out of Scope — IDs vary per
  company, never hardcode.)
- **Seven tools give confidently wrong US answers for a Canadian:** Schedule C mapping
  (`qb_tax_summary`, `qb_schedule_c`, `qb_schedule_c_detailed` — Canada files **T2125**),
  `qb_estimate_quarterly_tax` (US brackets, 15.3% SE tax, IRS dates; typing state="CA"
  silently applies **California** rates), `qb_1099_contractor_report` (Canada: **T4A**
  box 048, due end of February), `qb_depreciation_schedule` and
  `qb_vehicle_depreciation_calculator` (MACRS/Section 179; Canada uses **CCA classes** with
  half-year rule / Accelerated Investment Incentive), `qb_home_office_calculator`
  (Form 8829, $5/sqft simplified method — neither exists in Canada; and CRA's
  cannot-create-a-loss rule applies), `qb_deduction_finder` (US-only deductions).
- **`qb_sales_tax_summary` can't produce what a CA bookkeeper actually needs** — a GST/HST
  return: no ITC (input tax credit) side, no net-tax computation, no GST34 line mapping.
- **Misc:** no multicurrency awareness (`CurrencyRef`/`ExchangeRate`); "EIN" surfaced where
  Canada has a CRA Business Number; the Cowork tax-prep skill is 100% US. (Note: the
  `minorversion` param is no longer a concern — since Aug 1, 2025 Intuit pins all Accounting
  API requests to minorversion 75 automatically; the stale `minorversion=65` in the web OAuth
  callback is harmless and can be dropped.)

### Things to check outside the codebase (possibly blocking Canadians TODAY)

1. **Intuit app country setting.** In the Intuit developer portal, "Countries you accept
   connections from" must include Canada, or Canadian users get *"This app is not set up to
   allow connections from your country"* during OAuth and can never connect. This may be a
   material chunk of the "signed up but never connected" cohort if Canadian signups are
   common. One OAuth app can serve both countries once enabled.
2. **Stripe/marketing**: pricing is USD-only (`layout.tsx` schema, pricing page). Not
   blocking, but worth CAD price presentation for conversion.
3. **Create a Canadian sandbox company** (developer.intuit.com → sandboxes → country: Canada)
   for testing — it comes pre-seeded with provincial tax codes.

### Recommended CA roadmap

**Phase 0 — unblock (≈1 week):**
- Enable Canada in the Intuit app settings; add a CA sandbox.
- Detect region at startup: `CompanyInfo.Country` + `Preferences.CurrencyPrefs.HomeCurrency`
  + `TaxPrefs`; stash on the connection record.
- Add `qb_list_tax_codes` / `qb_list_tax_rates` (query TaxCode/TaxRate/TaxAgency). Never
  hardcode code IDs — they vary per company (e.g. "HST ON" might be Id 5 in one company).
- Thread `tax_code` (per line) + `global_tax_calculation` (header) through invoice /
  credit memo / estimate / expense / bill creation; catch error 6000 and return actionable
  guidance. For US realms these params are simply omitted.
- Gate the US-only tax tools on region: for CA companies return "this is a US tax tool —
  here's the Canadian equivalent" instead of wrong numbers.

**Phase 1 — CA value (≈2–3 weeks):**
- `qb_gst_hst_return`: net tax computation mapped to GST34 lines (101 sales; 103/105 tax
  collected; 106/108 ITCs from purchase-side tax; 109 net) from TaxCode-tagged transactions,
  plus the `TaxSummary` report endpoint (non-US editions only; requires `agency_id` from the
  TaxAgency entity — run per agency, e.g. CRA and a provincial agency). Include 50% meals ITC
  rule and Quick Method awareness (≤$400k, e.g. 8.8% in Ontario, 1% credit on first $30k).
  Note: QBO's Sales Tax Centre filed returns/filing status are NOT exposed by the API — the
  return must be computed from transactions + TaxSummary; `TaxPayment` (CA/AU/UK only) gives
  payments against filed returns.
- `qb_t2125_summary`: T2125 line mapping (8521 advertising, 8523 meals 50%, 9281 vehicle,
  9936 CCA, 9945 business-use-of-home) as the CA twin of `qb_schedule_c`.
- `qb_cca_schedule`: CCA classes (8/10/10.1/12/14.1/50/54), half-year rule + AII/immediate
  expensing (Bill C-15, property acquired ≥ Jan 1 2025), 2026 Class 10.1 ceiling $39,000.
- `qb_t4a_contractor_report`: T4A box 048 (and T5018 for construction), due end of February.
- CA instalment estimator: CPP 11.9% base + CPP2 8% (2026: YMPE $74,600, YAMPE $85,000),
  CRA instalment dates Mar/Jun/Sep/Dec 15, $3,000 threshold; CRA per-km rates (2026:
  73¢/67¢, territories 77¢/71¢); home-office rules (no loss creation, carryforward).
- Multicurrency display: show `CurrencyRef` + `ExchangeRate`; CAD home currency.
- Rewrite the Cowork tax-prep skill with a CA branch; swap "EIN" → "Business Number" for CA.

**Phase 2 — polish:** CAD pricing display, `en_CA` locale, CA-specific onboarding copy,
marketing page for Canadian bookkeepers (QBSE/Solopreneur don't exist in Canada — genuinely
underserved segment).

**Engineering caveat:** `server.py` and `mcpb/src/accountingqb/server.py` are ~7k-line
near-duplicates. Extract the shared core (or make one the source of truth with a build step)
*before* the CA work, or every change lands twice and diverges.

**Also time-sensitive (all users, not just CA):** Intuit's modernized Reports API serves all
report responses after **Aug 31, 2026** — validate report parsing against it now.

## Part 3 — Distribution: what the 2026 MCP ecosystem changes

### Recommended target architecture (two tiers, one product)

**Tier 1 (growth funnel): remote MCP connector.**
Build a stateless Streamable HTTP MCP server (target the 2026-07-28 spec profile) in front
of the existing hosted OAuth backend, and submit it to **Anthropic's Connectors Directory**.
This is the best conversion UX that exists: one click "Connect" → Intuit OAuth → done. No
Python, no uv, no terminal, no config file. It works on claude.ai, Desktop, mobile, and —
critically — **Claude Cowork web/mobile, which cannot reliably run local MCP servers**.
Custom connectors work on every plan (Free is limited to one). Position honestly as
"zero-retention pass-through — we never store your books" (distinct from the local tier's
"never touches our servers").

**Tier 2 (privacy flagship): the .mcpb desktop extension, ported to TypeScript.**
Claude Desktop bundles Node.js; it does not bundle Python, and the current
`"command": "uv"` manifest assumes uv is installed (plus a known Windows uv race bug).
A Node port eliminates the entire runtime-prerequisite class of failures and makes the
extension truly one-click from Claude Desktop's extension directory. Keep the existing
hosted-OAuth-broker → local token handoff so QuickBooks data flows device↔Intuit directly —
this "hosted OAuth broker + local execution" pattern is genuinely differentiated (all hosted
competitors proxy data; all local competitors require bring-your-own-Intuit-app; Intuit
production apps reject localhost redirect URIs, so your broker is the only clean shape).
During the Intuit production app assessment, get written confirmation that device-resident
tokens are acceptable.

**Multiplier: Cowork plugin + Skills.**
Restructure `cowork-plugin/` to the official `.claude-plugin/plugin.json` format (current
schema is non-standard) with `.mcp.json` pointing at the remote connector, bundle the
skills (month-end close, tax prep — with the CA branch, reconciliation), and submit to the
plugin directory. Anthropic's own data shows a third of Cowork usage is business-process
work — exactly this audience. Skills are also the practical answer to the 94-tool context
problem (Claude Code already defers large tool sets behind search; short, keyword-rich tool
descriptions help discovery).

**Deprioritize:** the `setup.py` wizard as a recommended path (keep the repo for
credibility/self-hosters); MCP registries (Smithery, etc.) are developer-SEO only; MCP
sampling is deprecated — don't build on it. **MCP Apps** (HTML UI in tool results, live in
Claude since Jan 2026) is a strong v2: an interactive P&L/dashboard widget.

**Directory review practicalities:** reviewers functionally test *every* tool; 94 tools =
long review. Every tool needs `title` + `readOnly`/`destructive` annotations. Provide a QBO
sandbox test account + runbook + example prompts. Reviews take weeks→months; start both
submissions early. Consider a curated core toolset for the reviewed build.

**Strategic check:** Intuit and Anthropic announced a partnership; verify whether a
first-party QuickBooks connector ships inside Claude. If it does, the moat is the 94
workflow tools, the skills layer, CA tax depth, and the local-execution privacy tier — not
basic connectivity. Price and message accordingly.
